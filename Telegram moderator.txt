Telegram Moderator Note

Purpose
- Capture the implementation already built so far.
- Cross-check it against the corrected architecture before any production code changes.
- Preserve the current monetization model while separating control-plane and runtime responsibilities correctly.

- Owner UI groundwork for a moderator add-on was added in the panel admin area.
- Moderator draft/settings persistence was added under panel settings.
- A Telegram webhook route was added for runtime event handling.

- The current implementation is functionally a Telegram moderator scaffold, but the actor model is still too collapsed.

Cross-Check Against the Corrected Architecture

1) Preserve Innvil's monetization model
- Keep the existing commission/rental/entitlement infrastructure.
- Do not create a separate billing system for the Virtual Moderator.
- Monetization must feed entitlement checks only.
- Runtime logic must not branch on commission vs rental directly.
- This means the existing monetization flow should stay in place, but it must sit above the product/runtime layer.

2) Clarify the meaning of Innvil is the manager
- Product level: Innvil owns/provides/manages the Virtual Moderator SaaS.
- Telegram level: Innvil runs a Telegram Manager Bot as control plane.
- Customer communities should be moderated by subscriber-owned managed bots, not by the Innvil Manager Bot.
- These are compatible roles, but they must not be collapsed into one runtime identity.

3) Virtual Moderator runtime is not moderation-only
- The runtime should be a Community Agent Runtime, not just a moderation engine.
- It must support conversation, answers, reactions, publishing, proactive revivals, and moderation.
- Moderation is one capability among several.

4) Preserve the reusable moderator model
- One VirtualModerator can deploy to many communities.
- One Telegram bot identity should be reusable across many deployments of the same moderator.
- Creating another deployment must not provision another bot.
- Creating another distinct moderator may require another Telegram bot identity.

5) Community must not live on VirtualModerator
- communityHandle and communityId do not belong on the reusable moderator entity.
- Community must be separate from the moderator.
- The relationship belongs on ModeratorDeployment.
- The moderator can exist with zero, one, or many deployments.

6) Finalize the domain separation
- VirtualModerator: reusable product identity.
- ModeratorPersona: reusable base personality.
- TelegramBotIntegration: subscriber-owned Telegram bot identity and credentials.
- Community: platform/community record.
- ModeratorDeployment: one moderator assigned to one community.
- DeploymentState: community-specific runtime state.
- CommunityMemory: deployment/community scoped memory.
- The current implementation still collapses some of these into one record and must be refactored.

7) Do not collapse deployment into another giant JSON object
- The current moderator settings object is too broad.
- Reusable config, community assignment, community-specific state, and platform identity must stay separate.
- The note here is to preserve the distinction before any schema work begins.

8) Add the missing Community Coordinator
- One community may have multiple deployed moderators.
- The system should normalize a CommunityEvent first.
- Then it should load eligible deployments.
- Then a Community Coordinator should select zero or one moderator normally.
- The decision pipeline should run only for the selected moderator.
- Zero selected moderators must be a valid outcome.

9) Do not multiply AI calls by moderator count
- A single message must not fan out to every moderator.
- Deterministic filtering and lightweight routing should happen first.
- Then only one selected moderator should run a decision pipeline when needed.

10) Preserve the platform-agnostic intelligence layer
- Telegram should act as an adapter.
- Raw Telegram Update objects should not flow deeply through the intelligence layer.
- The runtime should use CommunityEvent and CommunityAction abstractions.
- This is important so Discord or other platforms can be added later without rewriting the intelligence core.

11) Separate the two Telegram event domains
- Control plane: managed bot lifecycle, provisioning, ownership confirmation, credential rotation, recovery.
- Community runtime: message handling, replies, edits, reactions, moderation, publishing.
- The current implementation mixes these responsibilities and must be separated.

12) Correct credential architecture
- Innvil Manager Bot credential: Innvil-owned infrastructure secret.
- Subscriber managed-bot credential: tenant/integration-scoped secret for the customer-owned bot.
- Use encrypted at rest storage for managed-bot credentials.
- There must not be one global TELEGRAM_BOT_TOKEN acting as every customer's moderator.

13) Outbound action identity
- Actions must execute as the selected subscriber-owned bot identity.
- The Innvil Manager Bot must not perform community moderation actions as itself.
- Replies, deletes, bans, restrictions, publishing must resolve through the selected bot integration.

14) Permission checks belong to deployments/communities
- Permissions are per community deployment, not global.
- The same bot may have different permissions in different communities.
- Do not infer moderation ability from token validity alone.

15) Correct moderation state semantics
- Review moderator_spam_hits carefully.
- Decide whether state belongs to tenant + community + Telegram user, or whether deployment scope is required.
- Do not blindly attach deploymentId to everything without checking the semantic ownership.

16) Entitlements and runtime lifecycle
- Payment/monetization logic determines entitlement.
- Runtime logic checks capability, not plan type or monetization mode.
- Access expiration should stop service access, but should not destroy customer-owned Telegram bot identity.

Final Architecture Review Summary

A. Final domain model
- Tenant already exists conceptually in Innvil.
- VirtualModerator should be a reusable product entity.
- ModeratorPersona should hold reusable personality traits.
- TelegramBotIntegration should represent the subscriber-owned bot identity and credential reference.
- Community should represent the target Telegram community independently.
- ModeratorDeployment should connect one VirtualModerator to one Community.
- DeploymentState should hold runtime-specific state.
- CommunityMemory should be scoped by deployment/community, not by the reusable moderator.
- The current implementation already has pieces of this, but they are not yet separated cleanly in storage or code.

B. Final Telegram actor model
- Innvil Manager Bot: control plane only.
- Subscriber-owned managed bot: the visible runtime bot inside customer communities.
- Innvil runtime: intelligence and orchestration layer.
- Community: the Telegram group/channel being served.
- Virtual Moderator: the product persona/configuration.
- Deployment: the assignment of moderator to community through a specific bot integration.

C. Final inbound event flow
- Telegram update -> adapter -> normalize CommunityEvent -> resolve bot integration -> resolve community -> load deployments -> Community Coordinator -> choose zero or one moderator -> run selected decision pipeline -> produce CommunityAction.

D. Final outbound action flow
- CommunityAction -> resolve deployment -> retrieve encrypted managed-bot credential server-side -> execute as the selected customer-owned Telegram bot identity -> return result.

E. Final credential model
- Manager credential: Innvil infrastructure secret.
- Managed-bot credential: encrypted tenant/integration secret.
- Reuse existing encrypted secret patterns already used elsewhere in the repo.

F. Final Community Coordinator design
- Candidate discovery should be fast and deterministic.
- Zero-or-one selection should be normal.
- Deterministic filters should run before any AI call.
- Cost should not scale linearly with moderator count.
- Multiple moderators in one community should be supported without multiplying calls.

G. Monetization/entitlement boundary
- Monetization ends at entitlement.
- Runtime reads capability flags only.
- Commission and rental modes stay in the existing product infrastructure.
- Telegram runtime must not know which monetization path produced the entitlement.

H. Existing-file disposition
- app/api/webhooks/telegram/route.ts -> MODIFY or REPLACE.
  - Reason: keep the webhook concept, but split control-plane vs runtime responsibilities.
- src/lib/moderator/telegram.ts -> REPLACE.
  - Reason: it currently collapses manager bot, managed bot, community, and deployment into one runtime path.
- src/lib/moderator/provisioning.ts -> MODIFY.
  - Reason: it should become the reusable domain model layer, not a flattened all-in-one record.
- src/lib/actions/moderator.ts -> MODIFY.
  - Reason: persistence should write the corrected model and not store community on the reusable moderator.
- src/components/panels/admin/AdminTabs.tsx -> MODIFY.
  - Reason: the owner UI must reflect the corrected product model and deployment setup.
- supabase/migrations/0043_moderator_spam_hits.sql -> REPLACE or MODIFY.
  - Reason: the moderation state table needs a final semantic review for deployment/community scope.

I. Schema migration proposal
- Add or split tables/records for:
  - VirtualModerator
  - ModeratorPersona
  - TelegramBotIntegration
  - Community
  - ModeratorDeployment
  - DeploymentState or equivalent scoped runtime state
- Rework spam-hit state so its keys match the true semantic owner.
- Reuse existing encrypted secret storage for managed bot credentials.
- Do not keep the flattened community-on-moderator design if it has no shipped data dependency.

J. Small correction implementation plan
- Step 1: finalize the domain model and persistence shape before any code change.
- Step 2: separate manager/provisioning flow from runtime/community flow.
- Step 3: introduce the Community Coordinator and event normalization.
- Step 4: rewire outbound actions to execute as the selected customer-owned bot identity.
- Step 5: only then revisit UI polish, proactive chat, memory, analytics, and other expanded behaviors.

Implementation Status
- No production code should be changed yet.
- This note is the current working reference for the corrected architecture.
